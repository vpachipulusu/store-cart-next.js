# StoreCart — implementation plan

**Product:** StoreCart, a multi-merchant commerce SaaS. Merchants sign up, create organisations with several stores, and sell through their own storefronts.
**Jira:** project *Store Cart* (`KAN`) — backlog and key map in [backlog/](backlog/) ([jira-map.md](backlog/jira-map.md)).
**Last updated:** 2026-10-11 (adopted the vintasoftware/nextjs-fastapi-template backend).

## Decisions

| # | Decision | Choice |
|---|---|---|
| D1 | Tenant data isolation | One Postgres database per store (Neon), plus one platform database |
| D3 | Account structure | Organisation → Membership (OWNER / ADMIN / STAFF) → several Stores |
| D4 | Seller of record | Merchants, via Stripe Connect direct charges |
| D9 | Platform revenue | Subscription only (Stripe Billing on the organisation); `platform_fee_bps = 0` reserved for a future per-order fee |
| D10 | Frontend hosting | Vercel project rooted at `nextjs-frontend/` |
| D13 | Backend hosting | **Vercel** Python serverless functions, rooted at `fastapi_backend/` (template's `api/index.py` + `vercel.json`) |
| D14 | Frontend → backend | Only from the Next.js server (server components, actions, route handlers); the browser never calls FastAPI |
| D15 | Data access | SQLAlchemy 2 async + asyncpg, `NullPool` (serverless), Alembic with two trees: `platform` and `store` |
| D16 | API contract | FastAPI OpenAPI → `generate_openapi_schema` (+ `watcher.py` in dev) writes `nextjs-frontend/openapi.json` → `@hey-api/openapi-ts` generates a typed fetch client; CI fails when stale |
| D17 | Response envelope | `{ success, data?, error? }` kept so frontend components barely change |
| D18 | Background jobs | Upstash QStash calls signed backend endpoints; each step fits in one serverless invocation |
| D19 | File storage | Cloudflare R2, presigned uploads issued by the backend |
| D20 | Tooling | uv, ruff, mypy, pytest (+ pytest-asyncio), **pre-commit hooks**, **Docker Compose** for local dev, Sentry |
| D21 | Merchant auth | **Firebase** (kept). FastAPI verifies the Firebase session cookie; the template's fastapi-users is removed |
| D22 | Email | Resend (as the boilerplate); the template's fastapi-mail is removed |
| D23 | Folder names | `nextjs-frontend/` and `fastapi_backend/` (template convention) |

### Foundation scope (council decision, 2026-10-11)

Option A with a real-database spike was chosen unanimously over porting all ~92 boilerplate actions.

- **In Foundation:** E1, E2, auth/session, profile/settings, 2FA, organisation billing, tenant-aware audit log, minimal admin (users, subscriptions), E6 (no secrets in the frontend).
- **Security exit rule:** every one of the 10 pages that queried Prisma directly is moved to the API or switched off; deferred features are switched off, never left on Prisma.
- **Cut and redesigned later (E22, KAN-114):** SEO meta, redirects, email templates (per store), feature flags, app settings, analytics/system stats, notifications, data export.
- **Spike KAN-115** (≤3 days, after KAN-30 + KAN-112): route one request to a second Neon store database on Vercel and record median/p95 latency including cold starts. If unacceptable, revisit hosting or one-database-per-store (dissent: shared DB + `store_id` + row-level security) before E7.
- **Estimate:** Foundation ≈ 4–5 weeks (was 8–10).

**Foundation start order:** KAN-25 (commit the move, `.gitignore` fix) → KAN-29 (ADR-001, widened) → KAN-112 trial deploy + KAN-113 (parity inventory and behaviour baseline) in parallel → KAN-111 (pre-commit) → KAN-27 (CI with gate job) → KAN-30 (template adaptation, with the session-provider seam) → **KAN-115 (spike)** → KAN-31 / KAN-33 → KAN-32, KAN-34, KAN-35, KAN-26, KAN-28 → E3, E4, E5 (trimmed), E6.

## Serverless consequences (Vercel backend)

- No long-lived connection pools: `NullPool` per request, Neon pooled endpoints for platform and store databases.
- Store provisioning runs as QStash-triggered steps (create DB → migrate → mark ready), each idempotent and short.
- Platform migrations run at deploy; **store migrations run from a GitHub Actions job** (`migrate_stores`), never inside a request.
- Rate limiting and caches use Upstash Redis (HTTP), not in-process memory.

## Risks

| Risk | Severity | Mitigation |
|---|---|---|
| Data crossing between merchants | Critical | `require_merchant` before `get_store_session`, lint ban on direct engine creation, tenant isolation suite (E7.7) |
| Preview deployments migrating or reading production data | High | Separate preview database; production deploys only from the release workflow |
| Store databases on mixed schema versions | High | Backward-compatible migrations, batched runner that stops on failure, per-store version tracking |
| Serverless time limits during provisioning | Medium | Step-wise QStash jobs with retries and a `failed` state |
| Old dependency pins in the template | Medium | Upgrade in E2.1 before building on it |
| Frontend/backend contract drift | Medium | Generated client + CI staleness check + pre-commit hook |
